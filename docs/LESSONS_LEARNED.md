# Lessons Learned: FPGA Acceleration Development

A collection of technical insights, debugging war stories, and architectural decisions from the development of the FPGA Trading Portfolio.   

---

## 0. The Design Philosophy: Why 28nm?

**"Constraint drives creativity."**

A deliberate choice was made to validate this architecture on the **Zynq-7000 (28nm)** rather than modern Ultrascale+ (16nm) silicon.

*   **The Challenge:** Older silicon is unforgiving. Achieving **250 MHz** compute performance on Artix-7 fabric requires manual `DSP48E1` pipelining, careful floorplanning, and logic replication. These issues are often masked by the raw speed of modern 16nm chips.
*   **The Proof:** Closing timing on this mature node demonstrates rigorous RTL optimization skills. It proves the design is fundamentally sound, not just relying on process node improvements.
*   **The Payoff:** If logic closes timing at 90% utilization on 28nm, it will fly on 16nm with massive margins for power reduction and feature scaling.

## 1. Timing & Constraints

### The "Behavioral Synthesis" Trap (Project 12)
**Context:** Implementing the Systolic Processing Element (PE).   
**Issue:** Writing standard SystemVerilog `result <= a * b + c` resulted in Vivado inferring logic that failed timing at 250 MHz. The tool struggled to pack the pipeline registers correctly into the DSP slices.   
**Solution:** Manually instantiating the `DSP48E1` primitive.   
**Lesson:** For performance-critical arithmetic pathways, do not rely on the synthesizer's inference. Explicitly controlling the `AREG`, `BREG`, `MREG`, and `PREG` pipeline attributes is mandatory for closing timing at high frequencies.   

### RGMII Clock Phase Alignment (Project 09)
**Context:** Interfacing with the Realtek RTL8211E PHY.   
**Issue:** The RGMII standard requires the data to be stable at the clock edge (DDR). However, trace lengths on the board introduced skew, causing setup violations.   
**Solution:**   
1. Used `IDELAYE2` on the input **clock** line (`rgmii_rxc`) to shift the capture window.   
2. Inverted the RX clock locally at the IDDR (`.C(~gmii_rx_clk)`) to effectively shift the capture window by 180 degrees (4ns at 125MHz), placing the sampling edge in the center of the data "eye".   

**Lesson:** Source-synchronous interfaces are never "plug and play." Always budget time for dynamic phase alignment or static eye-centering.

## 2. Linux & PCIe Integration

### The Custom Device ID Black Hole (Project 11)
**Context:** Loading the Xilinx XDMA driver on a host Linux machine.   
**Issue:** The driver refused to load, claiming "No device found," despite `lspci` showing the card at `03:00.0`.   
**Root Cause:** The default XDMA IP core uses Device ID `0x9022`. The user-space driver was looking for this ID. However, the Board Support Package (BSP) had customized the ID to `0x7015`.   
**Fix:** Patched the `pci_ids` table in `xdma_mod.c` and recompiled the kernel module (`xdma.ko`).   
**Lesson:** Software assumes defaults; FPGA engineers change them. Always align your PCIe IDs (Vendor/Device/Subsystem) effectively between the constraints file and the driver code.   

### ARP Cache Invalidation (Project 11/13)
**Context:** Sending UDP packets from Host to FPGA.   
**Issue:** Packets were being generated by the Python script but never arriving at the FPGA MAC.   
**Root Cause:** The OS ARP table. The Linux kernel didn't know the MAC address of the link-local FPGA IP and was sending ARP Who-Has requests. The FPGA had no ARP stack implemented (Raw UDP only).   
**Fix:**    
1. **Short Term:** Static ARP entry (`arp -s 192.168.1.10 00:0a:35:00:01:02`).   
2. **Long Term:** Used `scapy` to craft raw Layer 2 frames, bypassing the OS IP stack entirely.

## 3. Reliability & Verification

### The "Ghost" Valid Signal (Project 13)
**Context:** Validating the NPU trigger logic.   
**Issue:** The trigger output fired sporadically or stuck at zero even when input data was valid.   
**Root Cause:** Twofold:
1.  **Uninitialized Memory:** DSPs were multiplying incoming data by zero/garbage weights. Simulation initialized these, silicon did not.
2.  **Zero-Padding:** Ethernet frames < 64 bytes are padded with zeros by the OS. The parser's `valid` signal remained high during padding, flooding the pipeline with zeros and diluting the inference result.
**Solution:**   
1.  **Control Plane Injection:** Used a VIO core to manually drive weight registers post-boot, bypassing the potentially uninitialized AXI interface.
2.  **Auto-Clear Logic:** Implemented a 1-cycle strobe on the parser output to ensure only the signficant byte is ingested, dropping the zero-padding.   
**Lesson:** Silicon initialization is not guaranteed. Always verify with a known-good control source (VIO) before trusting the full software stack.   

### VIO vs. ILA for Debugging
**Comparison:**
*   **ILA (Integrated Logic Analyzer):** Great for "What happened?" (Capturing fast transients, like a packet arriving). Used for validating the RGMII RX timing.   
*   **VIO (Virtual I/O):** Great for "What if?" (Injecting valid signals manually). Used for stimulating the NPU without needing to create a full functional Ethernet packet generator first.   

**Lesson:** Use VIO to decouple subsystems. I was able to verify the NPU logic (Project 13) before the Ethernet MAC (Project 09) was fully working by injecting "fake" packets via VIO.

## 4. Coding Patterns

### Reset Bridges (Project 01)
**Concept:** Asynchronous Assert, Synchronous Deassert.   
**Code:**
```systemverilog
always_ff @(posedge clk or negedge rst_n_in) begin
    if (!rst_n_in) begin
        rst_meta <= 0;
        rst_n_out <= 0;
    end else begin
        rst_meta <= 1;
        rst_n_out <= rst_meta;
    end
end
```
**Why:** Ensures the reset signal enters the clock domain cleanly, preventing metastability when the system comes out of reset.   

### Gray Codes for CDC (Project 03)
**Concept:** Passing multi-bit counters between 100MHz and 33MHz domains.   
**Insight:** A standard binary counter can transition from `0111` (7) to `1000` (8). If sampled mid-transition, it might read `1111` or `0000` due to skew. Gray codes change only one bit at a time (`0100` -> `1100`), ensuring the sampled value is always valid (either the old value or the new value, never a glitch).

### Shift-Register Parsing vs. Absolute Byte Counting (Project 13)
**Context:** Parsing the Feature ID (e.g., "0050") from incoming Scapy UDP packets.
**Issue:** The initial parser rigidly waited for explicit byte offsets (e.g., `byte_counter == 50`). This failed on hardware due to variable preamble lengths, VLAN tags, or padding inserted by the NIC/OS stack.
**Solution:** Abandoned absolute offsets. Implemented a **Continuous Signature Scanner** using a 32-bit shift register. The parser shifts in `tdata` every cycle and asserts a match whenever `{old_bytes, new_byte} == TARGET_ID`.
**Lesson:** Never trust absolute network offsets. Always scan for signatures. "Be liberal in what you accept."

### Shift-Register Parsing vs. Absolute Byte Counting (Project 13)
**Context:** Parsing the Feature ID (e.g., `"0050"`) and payload value from incoming Scapy UDP packets in hardware.
**Issue:** The initial parser was designed to rigidly wait for `byte_counter == 42` to match the ID, and `byte_counter == 46` to extract the value. However, the physical hardware failed to match anything.
**Root Cause:** Network environments are inherently messy. The Linux OS, NIC drivers, or intervening switches silently inject 802.1Q VLAN tags, IP Options, or Ethernet padding into the frame, shifting the arbitrary "byte 42" offset backwards or forwards. Relying on an absolute byte count is brittle.
**Solution:** Abandoned explicit byte-offset counting. Instead, implemented a **Continuous Signature Scanner** using a 32-bit shift register. The parser continuously shifts in `s_axis_tdata` on every valid clock cycle, searching for the hex signature `{current_feature_id[23:0], s_axis_tdata} == 32'h30303530` anywhere in the stream. Because the Python sender rigidly packs the payload value exactly 4 bytes *after* the ID string, the FSM simply triggers a 3-cycle wait-state upon signature match and grabs the subsequent 4th byte.
**Lesson:** In hardware networking infrastructure, assume the packet size and header offsets will shift. Use sliding window signature matchers instead of hardcoded byte offsets to achieve bulletproof extraction.

### Dealing with Ethernet Zero-Padding Pulse Stretching (Project 13)
**Context:** Extracting valid 8-bit features and sending a `valid` pulse into the Systolic PE array.
**Issue:** Sending small test packets (< 64 bytes) resulted in "washed out" inference values, where the correct NPU math was immediately overwritten by zeros, causing false positive Class 0 triggers.
**Root Cause:** Ethernet mandates a minimum frame size of 64 bytes (CSMA/CD standards). When sending a 24-byte UDP packet, the OS/NIC automatically pads the remainder of the frame with `0x00`. Because the parser was just holding `valid` high as long as `s_axis_tvalid` was asserted, these trailing zeros flooded into the NPU pipeline.
**Solution:** Hand-crafted a 1-cycle auto-clear logic trap (`if (feature_valid) feature_valid <= 1'b0;`) that ensures the PE array only ingests exactly one valid byte per signature match, cleanly dropping the rest of the zero-padded Ethernet frame.
**Lesson:** Network standards have physical-layer quirks hidden from software developers. Always account for CSMA/CD mandatory zero-padding when dealing with short packets.

### The Deaf MAC: RGMII IDELAY Regression (Project 13)
**Context:** Bringing up the inference engine's physical Ethernet link.
**Issue:** Despite `tcpdump` showing outgoing traffic from the Linux host, the FPGA's raw MAC layer never detected the preamble (`0x55/0xD5`). The physical PHY was completely deaf.
**Root Cause:** A regression in the `rgmii_rx.sv` clocking primitives. The project was using an `IDELAY_VALUE` of `28` with no clock inversion. This 28-tap delay skewed the RGMII clock relative to the incoming data (by over 2.2ns), causing the MAC to sample exactly on the data transitions instead of the stable center of the data "eye". The MAC saw nothing but corrupted garbage bits.
**Solution:** Restored the working phase delay parameters from the Project 09 baseline. Reverting to `IDELAY_VALUE(0)` with `~gmii_rx_clk` centered the capture window perfectly, instantly bringing the physical link back to life.
**Lesson:** Hardware constraints and primitive configurations are brutally exact. A single parameter drift in IDELAY tap settings can completely blind the physical layer, making perfectly functional higher-level logic behave as if it's broken. When the system is entirely dark, start debugging at Layer 1.
